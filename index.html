Why these pieces exist

Snapshot + incrementals
On subscribe, the client gets one full snapshot of the book, then a stream of small incremental deltas it applies on top. Re-sending the whole book on every change would waste bandwidth; deltas keep steady-state traffic tiny.
One socket, one writer
Only the sender thread ever calls send(). The listener and the consumer hand it work through the queue — so frames from different producers can never interleave mid-message on the wire.
Sequence numbers
Every message carries a monotonic per-instrument seq. The client applies updates in order and can detect a re-snapshot boundary — the backbone of correct reconstruction.

The problem: TCP is a byte stream

TCP delivers a reliable, ordered stream of bytes — it has no idea where one message ends and the next begins. Protobuf is not self-delimiting: a parser can't find a message boundary on its own. So every frame on this wire is:

Big-endian is the network convention (htonl/ntohl) — both peers agree on byte order regardless of CPU endianness.

Receive path — how the client reassembles messages

recv_all(sock, hdr, 4)
Read exactly 4 bytes. recv() may return fewer bytes than asked (a short read) — recv_all loops until all 4 arrive.
n = ntohl(hdr)  // = 85
Decode the big-endian header into the payload length.
recv_all(sock, buf, n)
Read exactly n payload bytes — again looping over short reads until the whole message is in.
msg.ParseFromArray(buf, n)
Hand protobuf a complete, exact-sized buffer. One whole message recovered; loop back for the next frame.
